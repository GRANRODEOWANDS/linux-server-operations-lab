# 第5弾：DNS・ネットワーク障害の切り分け

## 1. 検証目的

Linuxサーバから外部サイトへアクセスできない場合を想定し、ネットワーク接続とDNS名前解決を切り分ける方法を学ぶ。

今回は、正常なネットワーク接続を確認した後、応答しないDNSサーバへの問い合わせを意図的に実行し、DNSのタイムアウトを再現する。

その後、正常なDNS問い合わせとHTTPS通信を確認する。

## 2. 検証環境

- OS：Ubuntu Server 24.04
- 仮想環境：VirtualBox
- 対象サーバ：tokyo
- ネットワーク：NATおよびホストオンリーアダプター
- 検証対象ドメイン：`example.com`
- タイムアウト検証先：`192.0.2.1`

※ `192.0.2.1` は文書・検証用に予約されたIPアドレスであり、実際に稼働しているDNSサーバを停止したわけではない。

## 3. IPアドレスと経路の確認

まず、サーバのIPアドレスとルーティング情報を確認する。

```bash
ip -br addr
ip route
```

今回の検証環境では、主に次のネットワークを使用した。

```text
enp0s3 : 10.0.2.15（NAT）
enp0s8 : 192.168.56.11（ホストオンリー）
```

NAT側のデフォルトゲートウェイは `10.0.2.2` だった。

外部への通信に問題がある場合は、最初にIPアドレスと通信経路を確認することが重要である。

## 4. IP通信の確認

ゲートウェイへ通信できるか確認する。

```bash
ping -c 4 10.0.2.2
```

続いて、外部IPアドレスへ通信できるか確認する。

```bash
ping -c 4 1.1.1.1
```

実際の検証では、どちらも応答が返ってきた。

これにより、少なくとも今回の検証時点では、ゲートウェイおよび外部IPアドレスへのICMP通信が成功していることを確認した。

ただし、pingが成功しても、すべてのTCP・UDP通信が正常であるとは限らない。

## 5. DNS名前解決の確認

`example.com` の名前解決を確認する。

```bash
getent ahostsv4 example.com
```

続いて、DNSサーバの情報を確認する。

```bash
resolvectl status
```

今回の環境では、DNSサーバとして `192.168.188.1` などが表示された。

次に、DNS問い合わせを実行する。

```bash
dig example.com A
```

実際の検証では、次のような結果を確認した。

```text
status: NOERROR
example.com. IN A 104.20.23.154
example.com. IN A 172.66.147.243
```

`NOERROR` はDNS問い合わせが正常に処理されたことを示す。

Aレコードは、ドメイン名に対応するIPv4アドレスを表す。

※ IPアドレスは問い合わせ時点やDNS環境によって変わる場合がある。

## 6. DNSタイムアウトの再現

今回は、通常使用するDNS設定を変更せず、特定の宛先へ直接問い合わせを行った。

```bash
dig @192.0.2.1 example.com A +time=2 +tries=1
```

各指定の意味は以下のとおり。

- `@192.0.2.1`：問い合わせ先DNSサーバのIPアドレスを指定
- `example.com`：名前解決したいドメイン
- `A`：IPv4アドレスを問い合わせる
- `+time=2`：応答待ち時間を短く設定
- `+tries=1`：問い合わせの試行回数を指定

実際の検証では、DNS問い合わせがタイムアウトした。

この結果から、指定した宛先からDNS応答を得られなかったことが分かる。

ただし、タイムアウトだけで「DNSサーバが停止している」とは断定できない。通信経路やフィルタリングなども原因候補となる。

## 7. 通信経路の確認

タイムアウトした宛先への経路を確認する。

```bash
ip route get 192.0.2.1
```

今回の結果では、次の経路が表示された。

```text
via 10.0.2.2 dev enp0s3 src 10.0.2.15
```

これは、`192.0.2.1` 宛ての通信がNAT側のゲートウェイへ送られる経路として判断されていることを示す。

なお、この結果だけでは、宛先まで通信が届いたことは証明できない。

## 8. 正常なDNS問い合わせとHTTPS通信の確認

通常のDNS問い合わせを再実行する。

```bash
dig example.com A
```

実際の検証では、再び正常な応答を確認した。

続いて、HTTPS通信を確認する。

```bash
curl -I --max-time 10 https://example.com
```

今回の検証では、以下の結果を確認した。

```text
HTTP/2 200
```

さらに、DNS問い合わせを省略して接続先IPアドレスを指定する方法も試した。

```bash
curl -I --max-time 10 --resolve example.com:443:104.20.23.154 https://example.com
```

実際の検証では、HTTP/2 200を確認した。

`--resolve` は、指定したホスト名とポート番号に対して接続先IPアドレスを指定するオプションである。

これにより、通常のDNS名前解決に依存せずに、指定IPアドレスへのHTTPS接続を検証できる。

また、`-v` を使って接続先IPアドレス、TLS接続、証明書検証の様子も確認した。

## 9. 今回の検証で学んだこと

- IPアドレスへの通信と、ドメイン名の名前解決は別の確認項目
- `ip route` で通信経路を調べられる
- `ping` はICMP通信の確認に使えるが、すべての通信の正常性は保証しない
- `getent` や `dig` で名前解決を確認でき
